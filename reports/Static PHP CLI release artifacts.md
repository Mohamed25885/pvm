# Static PHP binaries ship checksums but no signatures

*Observed 2026-11-10. Facts marked **observed** were fetched live that day from dl.static-php.dev, the GitHub API, or workflow and source files. Statements marked **inference** are reasoning from those observations.*

static-php-cli (being renamed "StaticPHP") publishes prebuilt PHP binaries **only on dl.static-php.dev**, never on GitHub Releases. The current tree, `https://dl.static-php.dev/v3/php-bin/<set>/`, covers PHP 8.2 to 8.5 for Linux (musl static, plus a glibc 2.17 set), macOS, and **Windows x86_64 only**. The Windows builds come as single-file zips that hold just `php.exe` or `micro.sfx`. The only integrity material for those binaries is a **per-archive `.sha256` sidecar on the same host**, and only the newest patch release of each minor version has one. There are **no GPG, minisign, or cosign signatures, no published signing key, no Authenticode signing, and no GitHub attestations for PHP binaries**. Attestations exist only for the `spc` builder tool. The binaries are built by scheduled GitHub Actions in the project's own org repo, **`static-php/hosted`**. That is the correct current name: `static-php/static-php-cli-hosted` is an old name that GitHub redirects to the same repository. The builds check out a moving branch and upload to a DigitalOcean Spaces bucket with static keys. For PVM the conclusion is that a downloader can detect corruption and truncation, and can trace a file to a public CI run by hand. It **cannot cryptographically prove a binary came from that CI** rather than from anyone holding the bucket credentials. That gap belongs in PVM's trust decision and in its user-facing messaging.

## Binaries come from `static-php/hosted`, not the main repo

The notes disagreed on the name of the CI repo, so I checked it against the GitHub API on 2026-11-10 (**observed**). `GET repos/static-php/hosted` and `GET repos/static-php/static-php-cli-hosted` both return `full_name: "static-php/hosted"` with the **same repository ID (696755382)**. So `static-php-cli-hosted` is a previous name that GitHub redirects, and **`static-php/hosted` is canonical** ([GitHub API](https://api.github.com/repos/static-php/hosted)). Its default branch is **`master`**. It has no `main` branch, so links of the form `.../hosted/blob/main/...` do not resolve to the workflows. The main repo's README links the same repo's Actions as the direct-download source "or from a self-hosted server" ([README @ v3](https://github.com/crazywhalecc/static-php-cli/blob/v3/README.md)).

Two workflows publish the binaries, `v3-php-bin-unix.yml` and `v3-php-bin-windows.yml`. Both run on `workflow_dispatch` and on the cron `0 1 */3 * *`. Both check out **`crazywhalecc/static-php-cli` at `ref: v3`, a branch rather than a pinned commit**, build with `bin/spc build ...`, and push through `static-php/upload-s3-action@v1.0.0` to `v3/php-bin/<combination>/` using the repository secrets `AWS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_BUCKET` and `AWS_ENDPOINT` ([unix workflow](https://github.com/static-php/hosted/blob/master/.github/workflows/v3-php-bin-unix.yml), [windows workflow](https://github.com/static-php/hosted/blob/master/.github/workflows/v3-php-bin-windows.yml)). The job metadata of recent runs shows **GitHub-hosted runners** (runner group `GitHub Actions`), despite the "self-hosted" wording in the workflow names. The scheduled runs of 2026-11-07 and 2026-11-10 failed and the run of 2026-11-04 succeeded, so the cron does not guarantee a fresh build every three days ([hosted Actions runs](https://github.com/static-php/hosted/actions/workflows/v3-php-bin-unix.yml)). The main repo's own `build-unix.yml` and `build-windows-x86_64.yml` are manual builds that only upload Actions artifacts. Its `release-build.yml` publishes only the `spc` tool ([workflows @ v3](https://github.com/crazywhalecc/static-php-cli/tree/v3/.github/workflows)).

Downloads go through two redirects (**observed**). Cloudflare at dl.static-php.dev answers first with a 302 to `/down?path=...`, which then redirects to **`static-php-cli.fra1.digitaloceanspaces.com`**, an S3-compatible DigitalOcean Spaces bucket. Plain HTTP is 301-redirected to HTTPS, and the Spaces origin sends HSTS with preload ([sample download](https://dl.static-php.dev/static-php-cli/common/php-8.5.8-cli-linux-x86_64.tar.gz)). No public statement names who operates the host. The README says sponsorship money partly funds "the static-php.dev server" ([README @ v3](https://github.com/crazywhalecc/static-php-cli/blob/v3/README.md)). **Inference:** the host is run by the lead maintainer (Jerry Ma, `crazywhalecc`) or the `static-php` org.

## Windows gets two extension sets, one architecture, and one bare binary

The v3 tree has six sets (**observed**) ([v3/php-bin](https://dl.static-php.dev/v3/php-bin/), [README @ v3](https://github.com/crazywhalecc/static-php-cli/blob/v3/README.md)):

| Platform | Sets | SAPIs | Linking |
|---|---|---|---|
| Linux x86_64, aarch64 | common (37 ext), bulk (56), minimal (7) | cli, fpm, micro | musl, static |
| Linux x86_64, aarch64 | gnu-bulk (56) | cli, fpm, micro | glibc 2.17, dynamic |
| macOS x86_64, aarch64 | common, bulk, minimal | cli, fpm, micro | n/a |
| Windows x86_64 | spc-min (7), spc-max (50+) | cli, micro | n/a |

The Windows filename pattern is `php-<X.Y.Z>-<cli|micro>-win.zip`, with **no architecture in the name**. The packaging step is `Compress-Archive -Path "buildroot\bin\php.exe"`, so each zip contains **only `php.exe`**, with no `php.ini`, DLLs or `ext/` folder ([windows workflow](https://github.com/static-php/hosted/blob/master/.github/workflows/v3-php-bin-windows.yml)). On 2026-11-10 both Windows sets held 8.2.32/33/35, 8.3.32/33/36, 8.4.23/24/27 and 8.5.8/9/12. The spc-min `php-8.5.12-cli-win.zip` is 4.2M and the spc-max one is 9.6M ([spc-min JSON](https://dl.static-php.dev/v3/php-bin/spc-min/?format=json), [spc-max JSON](https://dl.static-php.dev/v3/php-bin/spc-max/?format=json)). **Inference:** some upstream patches are missing (8.2.34 on Windows, for example), which suggests each run builds only the current patch. PVM should list what exists instead of assuming every PHP release is available. The workflow sets no ZTS flag, which implies NTS builds, but the project does not state this explicitly.

Any directory listing becomes machine-readable when `?format=json` is appended. The entries carry `name`, `full_path`, `size` (a human-readable string such as `"9.6M"`), `last_modified` (no timezone) and `download_count`. **None of these fields is a hash** ([spc-max JSON](https://dl.static-php.dev/v3/php-bin/spc-max/?format=json)). This JSON comes from the listing server and is not a documented API. The URL layout has already moved once, from `static-php-cli/windows/spc-max/` to `v3/php-bin/spc-max/`. The current builds also come from builder version `3.0.0-alpha1`, while the latest stable GitHub release is 2.8.5 ([build-manifest.json](https://dl.static-php.dev/v3/php-bin/common/build-manifest.json), [Releases API](https://api.github.com/repos/crazywhalecc/static-php-cli/releases)). The legacy v2 tree at `/static-php-cli/` has deeper history, back to PHP 8.0.30, but it has **no checksums at all** and its last Windows upload was on 2026-06-10 ([legacy spc-min JSON](https://dl.static-php.dev/static-php-cli/windows/spc-min/?format=json)). One practical point from the research (**observed**): a request with Python's default urllib User-Agent got HTTP 403, while curl's User-Agent worked. PVM's Dart client should send an explicit User-Agent.

## Checksums arrived on 2026-10-23 and cover only the newest patches

The `.sha256` sidecars are new (**observed**). Commit `66cd3e63` in `static-php/hosted`, dated 2026-10-23, added a "Generate SHA-256 checksums" step to both workflows. On Windows the step uses `Get-FileHash -Algorithm SHA256`. Each archive gets its own `<archive>.sha256` file, because parallel matrix jobs would overwrite one shared sums file ([commit history](https://github.com/static-php/hosted/commits/master/.github/workflows/v3-php-bin-unix.yml)). The format is lowercase hex, two spaces, then the bare filename, which `sha256sum -c` accepts. For example, `php-8.5.12-cli-win.zip.sha256` reads `6c464e04...77368f  php-8.5.12-cli-win.zip` ([sidecar](https://dl.static-php.dev/v3/php-bin/spc-min/php-8.5.12-cli-win.zip.sha256)). Sidecar coverage is partial. Each Windows set has 24 zips but only 8 sidecars, covering cli and micro for 8.2.35, 8.3.36, 8.4.27 and 8.5.12. Older archives in the same directories have none. There is **no SHA512 file, no aggregate SHA256SUMS, and no hash field in `build-manifest.json`** ([v3/php-bin/common](https://dl.static-php.dev/v3/php-bin/common/)). The DigitalOcean ETag is a multipart ETag (`...-3`), not a file MD5, and no `x-amz-checksum-*` header is sent ([sample download](https://dl.static-php.dev/static-php-cli/common/php-8.5.8-cli-linux-x86_64.tar.gz)). No note compared a full archive against its sidecar, so an end-to-end match was not verified.

The maintainers have engaged with the request. In issue #1245 (still open), which asked for checksums, the owner replied on 2026-10-16 that hash verification and an SBOM "will be part of the v3 initiative". The sidecar commit followed a week later ([issue #1245](https://github.com/crazywhalecc/static-php-cli/issues/1245)). The owner's own issue #958 says "Signature is also suggested", but no signing exists ([issue #958](https://github.com/crazywhalecc/static-php-cli/issues/958)). No SBOM appeared in any v3 listing. The project documents no procedure for users to verify downloaded PHP binaries. A code search of the docs found checksum references only for build *inputs* ([repo](https://github.com/crazywhalecc/static-php-cli)).

## Provenance exists only for the builder tool

GitHub build-provenance attestations (Sigstore-backed) are real but cover the wrong artifact for PVM (**observed**). `release-build.yml` runs `actions/attest-build-provenance@v4` on the raw `spc`/`spc.exe` binary, and has done since commit `3ff9426e` on 2026-06-04. The attestations page lists 322 attestations, whose subjects are only `spc` and `spc.exe` ([release-build.yml](https://github.com/crazywhalecc/static-php-cli/blob/v3/.github/workflows/release-build.yml), [attestations](https://github.com/crazywhalecc/static-php-cli/attestations)). The 2.8.5 Windows `spc` exe predates that step, and looking up its digest in the attestation API returns 404 ([API](https://api.github.com/repos/crazywhalecc/static-php-cli/attestations/sha256:425b54ab857e21409c1fd9b818899ffebabd1e2817ef0a0ed5ae8a3d9f5b463b)). The hosted PHP workflows contain **no attest, cosign, gpg, minisign, signtool, SBOM or `id-token` step** ([hosted workflows](https://github.com/static-php/hosted/tree/master/.github/workflows)).

Windows code signing is absent. The PE header of the nightly `spc-windows-x64.exe` has an empty Certificate Table (offset 0, size 0), so it carries no Authenticode signature ([file](https://dl.static-php.dev/v3/spc-bin/nightly/spc-windows-x64.exe)). In issue #419 the owner said he knows "nothing about windows executable signing" and questioned whether signing a third-party `php.exe` would be appropriate ([issue #419](https://github.com/crazywhalecc/static-php-cli/issues/419)). **Inference:** `php.exe` inside the zips is unsigned. No signing step exists, but the binary was not extracted and inspected. SmartScreen and Defender reputation warnings are therefore plausible for PVM users.

The build inputs are only partly verified (**observed**). In v3, the php.net tarball is SHA-256-checked against php.net's release JSON, and GitHub release assets are checked against the API `digest` when one exists. Every other source type has no validator: git, GitHub tarballs, scraped file lists, plain URLs, PECL, and the prebuilt libraries from `static-php/package-bin`, which the Unix builds pull via `--dl-prefer-binary`. No hashes are pinned in config ([PhpRelease.php](https://github.com/crazywhalecc/static-php-cli/blob/v3/src/StaticPHP/Artifact/Downloader/Type/PhpRelease.php), [ArtifactDownloader.php](https://github.com/crazywhalecc/static-php-cli/blob/v3/src/StaticPHP/Artifact/Downloader/ArtifactDownloader.php), [HostedPackageBin.php](https://github.com/crazywhalecc/static-php-cli/blob/v3/src/StaticPHP/Artifact/Downloader/Type/HostedPackageBin.php)). By default the downloader falls back to `phpmirror.static-php.dev` when the primary source fails ([php-src.yml](https://github.com/crazywhalecc/static-php-cli/blob/v3/config/artifact/php-src.yml)). **Inference:** after a fallback, the release JSON and the tarball come from the same project host, so the php.net anchor is lost. Separately, the source-mirror workflow passes the AWS secrets to `shallwefootball/s3-upload-action@master`, a third-party action on a mutable ref ([download-cache.yml](https://github.com/static-php/hosted/blob/master/.github/workflows/download-cache.yml)). **Inference:** if those secrets reach the same bucket, which the secret names suggest but which is not visible, a compromise of that action could overwrite PHP binaries. No mechanism for reproducible builds exists, because the inputs float: a branch checkout, latest-stable dependency resolution, and the latest `package-bin` release ([artifact-model.md](https://github.com/crazywhalecc/static-php-cli/blob/v3/docs/en/develop/artifact-model.md)).

Governance is thin (**observed**). The project has no `SECURITY.md`. Private vulnerability reporting is disabled on both repos, although the contributing docs tell reporters to use it. There are zero security advisories ([contributing docs](https://github.com/crazywhalecc/static-php-cli/blob/v3/docs/en/contributing/index.md)). The main repo belongs to a personal account under the MIT license, and `static-php/hosted` has no license file ([LICENSE](https://github.com/crazywhalecc/static-php-cli/blob/v3/LICENSE), [hosted](https://github.com/static-php/hosted)). **Inference:** about two people do nearly all the work (crazywhalecc and henderkes), so the bus factor is about two. No reported build compromise was found, but that is an absence of evidence only.

## Trust-relevant facts for a downloader

**What a downloader can verify (observed):** TLS to Cloudflare and to the DigitalOcean Spaces origin, with HTTP redirected to HTTPS. For the newest patch of each minor version in `v3/php-bin/`, a SHA-256 match against a sidecar served from the same host. That detects corruption, truncation and an interrupted download. By hand, a downloader can also match the file's upload time to a public `static-php/hosted` run and read that run's checkout log for the exact `static-php-cli` commit. For the `spc` tool only, `gh attestation verify spc --repo crazywhalecc/static-php-cli` checks Sigstore-backed provenance, after extracting the raw binary.

**What a downloader cannot verify:** whether a PHP binary was produced by CI rather than uploaded by anyone holding the bucket keys. The sidecar shares the binary's origin, so an attacker who replaces one can replace both. A downloader also cannot verify any archive older than the 2026-10-23 sidecar rollout, anything in the legacy `/static-php-cli/` tree, which has no checksums, or a bit-for-bit rebuild. **Inference:** pinning SHA-256 values in PVM's own metadata, captured when PVM first sees a file, would add tamper detection for later downloads, but it would only prove the file has not changed since that capture.

**What is explicitly not checked by the project (observed):** No signatures exist (GPG, minisign or cosign), and no signing key is published. No attestations exist for PHP binaries. No Authenticode signing exists for the `spc` exe, and none is inferred for `php.exe`. No SBOM has been published yet. The nightly `spc` README states "We don't support any hash verification for nightly build" ([nightly README](https://dl.static-php.dev/v3/spc-bin/nightly/README.txt)). Most third-party build inputs are trusted over TLS alone. The CI pins `static-php-cli` to the moving `v3` branch, not to a commit. The bucket's IAM scope, versioning and object lock are not visible to anyone outside the project.
