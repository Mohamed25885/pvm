# Make the version folder PVM's core unit

*Synthesized 2026-11-10 from the notes in `research_notes/PHP sources and extensions per platform/`. It also draws on the earlier report and notes on Linux/macOS strategy, and takes the current draft design as context. Unless a claim is marked unverified, it was observed that day in a primary source (directory listings, APIs, repository source, archive inspection). No downloaded binary was executed.*

The best core design for PVM is a **per-version folder whose capabilities PVM probes**. Each slot is one directory holding `bin/php` (or `php.exe`), plus `phpize`, `php-config` and `pecl` when they exist. `pvm ext install` then picks its backend from what the folder can do, not from how the folder was made. This one abstraction covers every source PVM touches. A static-php download is a folder with no build tools. A PVM source build is a folder with full tools. A Windows zip is a folder that takes DLLs. A Plesk, Remi, Homebrew or pkgx install is a folder the user brings. The model matters because static-php `bulk`, the planned Linux/macOS default, lacks **six of the nine most-downloaded live PECL extensions**, xdebug and pcov among them. So the most common developer request lands on the weakest path. Building PHP from source for every install would fix that, but it costs about 5–10 minutes per version. It needs a C toolchain and 15–20 `-dev` packages installed with sudo. It also inherits a long tail of macOS and library-drift breakage that every source-based tool still carries. The evidence therefore supports keeping static-php as the fast default. On a static slot, PVM should refuse a non-bundled extension and name the two routes to a full folder, an opt-in `--from-source` install or `pvm link`, instead of the draft's rebuild-in-place. There is also a consequence the user has not yet weighed. **Almost no extension channel publishes a checksum**: not pecl.php.net tarballs, not the PECL Windows DLLs, not PIE's release assets. Under the trust rule, nearly every `pvm ext install` will need `--allow-unverified`.

## Six of the nine most-downloaded live PECL extensions are missing from static-php bulk

The only quantitative usage signal is the PECL all-time download table. Its top live packages are **redis (95.3M), imagick (93.7M), xdebug (85.8M), APCu (43.8M), pcov (32.1M), yaml (30.7M), memcached (30.1M), mongodb (28.1M) and amqp (19.1M)** ([PECL stats](https://pecl.php.net/package-stats.php)). Packagist's `php-ext` packages, the PIE ecosystem, rank them in nearly the same order: phpredis 557k, amqp about 376k across two names, pcov 230k, imagick 224k, apcu 197k ([Packagist search](https://packagist.org/search.json?type=php-ext&per_page=100)). xdebug has 508k on its own stats page ([xdebug stats](https://packagist.org/packages/xdebug/xdebug/stats.json)). Download counts skew toward CI-heavy extensions such as pcov and xdebug, which every Docker build fetches again. They also miss distro-packaged installs entirely, so they set the order but not the proportions.

Bundled extensions never show up in download counts, so framework requirements are the only evidence for them. Laravel 12 needs only bundled ones: ctype, curl, dom, fileinfo, mbstring, openssl, pdo, tokenizer, xml and others ([Laravel docs](https://github.com/laravel/docs/blob/12.x/deployment.md#server-requirements)). Magento 2.4.8 adds **bcmath, intl, gd, soap, sockets, sodium, xsl and zip** ([Adobe requirements](https://experienceleague.adobe.com/en/docs/commerce-operations/installation-guide/system-requirements)). Drupal requires **GD** ([drupal.org](https://www.drupal.org/docs/getting-started/system-requirements/php-requirements)). WordPress Site Health recommends intl, gd and zip, and **imagick**, the one PECL extension a major framework asks for ([class-wp-site-health.php](https://github.com/WordPress/wordpress-develop/blob/trunk/src/wp-admin/includes/class-wp-site-health.php)). The practical "must work on day one" set is therefore the bundled framework extensions plus redis, imagick, xdebug, pcov and apcu.

static-php's `bulk` set covers the framework side well: intl, gd, zip, bcmath, sodium, soap, xsl, pgsql, mysqli, opcache, plus redis, apcu, imagick, swoole, igbinary and msgpack. It has **no xdebug, pcov, yaml, memcached, mongodb, amqp, grpc, sqlsrv or ldap**. xdebug is `build-static: false` and can never be a static extension ([bulk README](https://dl.static-php.dev/v3/php-bin/bulk/README.txt), [ext-xdebug.yml](https://github.com/crazywhalecc/static-php-cli/blob/v3/config/pkg/ext/ext-xdebug.yml)). `pdo_sqlite` and `pdo_pgsql` exist only as swoole hooks in `bulk`, while the `common` set ships the real ones ([common README](https://dl.static-php.dev/v3/php-bin/common/README.txt)).

On a full folder (one with `php-config`), almost every extension is easy to get. The table gives the best route per platform. "PIE" means `pie install` against that folder's `php-config`, or on Windows its `php.exe`. "PECL DLL" means the `downloads.php.net/~windows/pecl/releases/<ext>/<ver>/` listing, which still produces DLLs for PHP 8.0–8.5 in 2026, for example xdebug 3.5.3 dated 2026-06-08 ([xdebug listing](https://downloads.php.net/~windows/pecl/releases/xdebug/)).

## PHP itself is solved on Windows and a trade-off on Linux and macOS

Windows is the easy platform. The php.net zips are relocatable and self-contained. `releases.json` publishes a **sha256 for every zip and for a `devel_pack`** ([releases.json](https://downloads.php.net/~windows/releases/releases.json)), and extensions arrive as DLLs that need no compiler. Nothing in the evidence argues for changing PVM's Windows source.

On Linux and macOS, no single channel is fast, rootless, relocatable, verifiable and extension-capable all at once.

Read down the columns and a clear split appears. **Every channel that ships `php-config` either needs root, lives inside another package manager's prefix, or is a source build**. pkgx is the one exception, and adopting its bottles would mean resolving its dependency closure, in effect reimplementing pkgx. So the realistic Linux/macOS sources are three. static-php is the fast default. A PVM source build gives a full folder on demand. `pvm link` adopts a full folder the user already has. Each of these produces a folder, and they differ only in what the folder can do.

## Building from source first trades seconds for minutes and a permanent patch backlog

A source-first PVM is attractive. Every slot would have a matching `php-config`, so `pvm ext install` would always work. Trust would rest on php.net's GPG signature and sha256, the strongest chain on Unix. The costs are measured, though.

docker-library's CI builds an 8.4 CLI image in about **5m47s on Debian trixie and 9m0s on Alpine** on a 4-vCPU runner with a warm mirror ([run 42429684274](https://github.com/docker-library/php/actions/runs/42429684274)). php-builder takes 7–10 minutes per SAPI ([run 42539085930](https://github.com/shivammathur/php-builder/actions/runs/42539085930)). A laptop's first run will be slower, but that was not measured. The build needs autoconf, bison, re2c, pkg-config and about 15 `-dev` packages on Debian. On macOS it needs around 15 Homebrew formulae and several `--with-*=$(brew --prefix …)` flags ([asdf-php README](https://github.com/asdf-community/asdf-php), [asdf-php #201](https://github.com/asdf-community/asdf-php/issues/201)). Under the "print the command, don't run sudo" rule, a first-time user would see a long prerequisite command before PVM installed anything.

The bigger cost is maintenance. php-build #784 reports that **"all versions of PHP fail to install on macOS"**, citing a BZip2 detection error, a space in `Library/Application Support` and BSD grep ([php-build #784](https://github.com/php-build/php-build/issues/784)). Its tracker also carries ICU 74 and libxml2 2.12 patches and a bash 5.3 abort. asdf-php and phpbrew carry the same class of Apple Silicon and OpenSSL bugs ([asdf-php #171](https://github.com/asdf-community/asdf-php/issues/171), [phpbrew issues](https://github.com/phpbrew/phpbrew/issues?q=macos+openssl)). Even the curated channels pin older libraries to keep old PHP building: pkgx pins libsodium below 1.0.19 and libxslt below 1.1.43 ([pantry recipe](https://github.com/pkgxdev/pantry/blob/main/projects/php.net/package.yml)). Source-first means owning that patch set forever. Windows cannot use the path at all without an MSVC toolchain, and it does not need to.

Every tool that users describe as "just works" prebuilds: Herd, php.new and setup-php. The four that build (phpbrew, php-build, asdf, mise) are the ones with the backlogs. That supports static-php first, with source builds opt-in.

The draft design adds a twist: a static slot is rebuilt in place when the user first asks for an extension. That moves the 5–10 minute build, plus the toolchain prompt, to the moment the user wanted a quick `xdebug`. Because xdebug and pcov are the commonest developer asks and `bulk` can never contain xdebug, this path would fire for most developers. The user's stated preference, refusing a single extension rather than starting a long full rebuild, argues for **refusing on static slots and naming the routes**: `pvm install 8.4 --from-source` (an explicit, opt-in full folder) or `pvm link`. The rebuild still exists. It is just never a side effect of `ext install`.

## Mature installers resolve the target explicitly, load-check before committing, and never fall back silently

The extension tools agree on a small set of practices, and most of them map directly onto PVM.

**Targeting.** PIE installs into whichever PHP runs it unless given `--with-php-config` (Unix) or `--with-php-path` (Windows). It reads the ABI tuple (API number, TS/NTS, compiler) from the "PHP Extension Build" line of the target's `phpinfo()` ([usage.md](https://github.com/php/pie/blob/1.6.x/docs/usage.md), [TargetPlatform.php](https://github.com/php/pie/blob/1.6.x/src/Platform/TargetPlatform.php)). Plesk users report that `/opt/plesk/php/8.2/bin/pecl install memcached` built against the wrong PHP. The handler-scoped `plesk bin php_handler --extension-install` fixed it ([Plesk forum](https://talk.plesk.com/threads/how-to-install-memcache-pecl-extension-for-php-not-memcached.367283/latest), [Plesk docs](https://docs.plesk.com/en-US/obsidian/administrator-guide/web-hosting/php-management/plesk-for-linux-installing-php-extensions-from-pecl.80036/)). The lesson is to pass the slot's own `php-config` or `php.exe` by absolute path every time, and to read the VS version from `php -i` rather than a table, since 8.6 moves to vs18 ([php-windows-builder](https://github.com/php/php-windows-builder)).

**Source order.** setup-php tries the platform's prebuilt package first, then compiles from PECL: ondrej apt on Ubuntu, the Homebrew tap on macOS, PhpManager plus PECL DLLs on Windows ([linux.sh](https://github.com/shivammathur/setup-php/blob/main/src/scripts/linux.sh), [darwin.sh](https://github.com/shivammathur/setup-php/blob/main/src/scripts/darwin.sh)). PIE prefers a prebuilt asset and falls back to source. That fallback has bitten users: a GitHub 403 rate limit silently turned a binary install into a compile, which led to requests for a binary-only flag ([pie #701](https://github.com/php/pie/issues/701), [pie #589](https://github.com/php/pie/issues/589)). PVM should never cross from download to compile without saying so, and it should honour `GITHUB_TOKEN`.

**Load check and rollback.** mlocati's installer compares `php -r 'return;'` stderr with and without a temporary ini line ([install-php-extensions](https://github.com/mlocati/docker-php-extension-installer/blob/master/install-php-extensions)). PIE restores the original ini if the extension does not load at runtime ([AddExtensionToTheIniFile.php](https://github.com/php/pie/blob/1.6.x/src/Installing/Ini/AddExtensionToTheIniFile.php)). setup-php backs up a DLL before replacing it and restores it on failure ([add_extensions.ps1](https://github.com/shivammathur/setup-php/blob/main/src/scripts/extensions/add_extensions.ps1)). mlocati also decides `zend_extension` versus `extension` from the `zend_extension_entry` symbol rather than from the extension's name.

**Layout.** PIE put a DLL in `C:\ext` because `extension_dir = "ext"` was relative ([pie #451](https://github.com/php/pie/issues/451)). It cannot find an extension path for Herd at all ([pie #504](https://github.com/php/pie/issues/504)). Windows locks loaded DLLs, so a reinstall fails while a server is running ([pie #190](https://github.com/php/pie/issues/190)). PVM controls its own layout, so it avoids all three. It should write an absolute `extension_dir`, keep one ini file per extension in a PVM-owned scan dir (disable by renaming to `.disabled`, as phpbrew does ([ExtensionManager.php](https://github.com/phpbrew/phpbrew/blob/master/src/PhpBrew/Extension/ExtensionManager.php))), put dependency DLLs next to `php.exe` instead of on PATH, and detect a running PHP before replacing a DLL.

**Integrity.** This is where the user's trust rule meets reality. pecl.php.net pages list tarballs with no checksum or signature ([redis page](https://pecl.php.net/package/redis)). The PECL Windows listings carry no `.sha256` or `.asc` ([xdebug 3.5.3](https://downloads.php.net/~windows/pecl/releases/xdebug/3.5.3/)). PIE drops Composer's dist checksum when it switches to a release asset. Its only integrity mechanism is a SHA-256 of the installed binary, which it records and checks before uninstalling ([OverrideDownloadUrlInstallListener.php](https://github.com/php/pie/blob/1.6.x/src/ComposerIntegration/Listeners/OverrideDownloadUrlInstallListener.php), [UninstallUsingUnlink.php](https://github.com/php/pie/blob/1.6.x/src/Installing/UninstallUsingUnlink.php)). Only Homebrew bottles (sha256 in the formula) and signed apt/RPM repos give a publisher-side check, and those only apply to PHPs from those package managers. Under the trust rule, `pvm ext install` from PECL, PIE or the DLL service is **always an unverified install**. PVM should copy PIE's local hash record and refuse to overwrite or remove a binary whose hash changed. Whether any extension publishes GitHub artifact attestations was not checked. If some do, that would be the only route to a verified PECL-style install.

**Smaller lessons.** Map short names to packages (`redis` → `phpredis/phpredis`) with PIE 1.6's extension map, and show which package was picked ([usage.md](https://github.com/php/pie/blob/1.6.x/docs/usage.md)). Accept `xdebug-3.4`, `^3` and `@stable`-style constraints, as mlocati, setup-php and Plesk all do. Fail fast with distinct exit codes for "no build for this ABI", "build tools missing", "built but failed to load" and "network or rate limit". PIE's open issue about varying exit codes shows the pain otherwise. Mark ZTS-only extensions such as parallel as unavailable on NTS slots ([special-requirements](https://github.com/mlocati/docker-php-extension-installer/blob/master/data/special-requirements)).

## The per-version folder model unifies static, built and linked PHP

Hosting panels and package managers converged on one shape long ago. Plesk keeps each version under `/opt/plesk/php/X.Y/` with its own `bin/pecl`. cPanel EA4 uses `/opt/cpanel/ea-php##/root/usr/bin/pecl` with a per-version `php.d` ([EA4 layout](https://docs.cpanel.net/ea4/basics/easyapache-4-file-system-layout/)). Remi installs SCL versions side by side under `/opt/remi` ([Remi FAQ](https://blog.remirepo.net/pages/English-FAQ)). Homebrew's `php@8.3` runs `pear config-set` on `ext_dir`, `php_ini` and `bin_dir` so that `$(brew --prefix php@8.3)/bin/pecl install` targets only 8.3 ([php@8.3.rb](https://raw.githubusercontent.com/shivammathur/homebrew-php/main/Formula/php@8.3.rb)). Laragon simply asks users to unzip PHP versions into `bin\php` ([Laragon docs](https://laragon.org/docs/multi-version)). The exact Plesk sub-paths are unverified. Debian/ondrej is the exception: it uses suffixed binaries (`php8.3`, `phpize8.3`, `php-config8.3`) with one shared `pecl` that needs `-d php_suffix=8.3` ([mwop.net](https://mwop.net/blog/2019-04-30-ondrej-multiversion-php.html)).

Version managers adopt such folders cheaply but blindly. `mise link node@24 <path>` symlinks a directory in, rbenv and phpenv accept any directory under `versions/`, and none of them documents any validation ([mise link](https://mise.jdx.dev/cli/link.html), [phpenv](https://github.com/phpenv/phpenv)). PVM can do better with a short probe:

1. Find `bin/php` or `php.exe`.
2. Run it once to read `PHP_VERSION`, ZTS, architecture, `PHP_EXTENSION_DIR` and the loaded ini files.
3. On Unix, check that sibling `phpize` and `php-config` exist and that `php-config --prefix` equals the folder.
4. Check whether the folder is writable by the user.

Store the result in the install record. Display and slot rules come straight from it: the probe yields `8.3 (8.3.x)`, a linked folder fills the 8.3 slot, and `pvm update 8.3` refuses for it.

The model has real limits, and the design must name them. **A Unix PHP is not relocatable.** The prefix, ini path, scan dir and extension dir are compiled into the binary and written as absolute paths into `phpize` and `php-config` ([Debian phpize.m4](https://sources.debian.org/src/php8.4/8.4.16-1/scripts/phpize.m4)). Nix had to patch `--includedir` for that reason ([nixpkgs commit](https://git.uninsane.org/colin/nixpkgs/commit/b330329768cc753b6bd8f0e6e3f398382566f7c8)). So "plug in" must mean link, never copy, and a prefix mismatch must be flagged as "runs, but pecl/phpize may target the wrong place". A PVM source build should use `--prefix=<slot>`, `--with-config-file-path=<slot>/etc` and `--with-config-file-scan-dir=<slot>/etc/conf.d`, then run `pecl config-set` the Homebrew way. Moving `PVM_HOME` then requires a rebuild. ondrej installs need a second, binary-path form of link. And PVM cannot own a linked folder's `php.ini`, so its per-version ini either layers onto the folder's own scan dir or stays out of the way. PHP's `PHP_INI_SCAN_DIR` can append to the compiled default rather than replace it, but that behaviour is unverified here and needs a test.

Against these limits, the gain is decisive. Static, source-built, Windows and linked slots become **one type with probed capabilities**, so `ext install`, `doctor`, `list` and the extension hint branch on "has `php-config`" and "is writable" instead of on four source kinds. The user's "bring your own folder" and "PVM produces the folder" become two producers of the same thing.

### How `pvm ext install <ext> [--version=X.Y]` works in each model

In both models the target is resolved the same way: `--version`, else the local `.pvm` version, else the global one, using the resolver `pvm php` already uses. If the extension is already in `php -m` for the target, PVM says so and stops.

| Step | Draft model (static default, rebuild in place) | Folder model (recommended) |
|---|---|---|
| Decide the backend | by source kind: static, source-built, linked or Windows | by probed capability: has `php-config`, writable, ABI tuple, OS |
| Windows slot | PIE `--with-php-path`, then the PECL DLL listing; unverified | same. Match `X.Y-{nts\|ts}-vsNN-{x64\|x86}` and accept PIE's `x86_64` and either order; on 404, list the ABIs that do exist; dependency DLLs go next to `php.exe` |
| Unix slot without `php-config` (static) | prompt, then rebuild PHP from source in place (5–10 min plus toolchain), then build the extension | **refuse**: "xdebug isn't in this build. Get a full 8.4 with `pvm install 8.4 --from-source`, or `pvm link 8.4 <folder>`." Exit non-zero |
| Unix slot with `php-config`, writable (PVM source build, Homebrew, pkgx, user-built) | PIE with the slot's `php-config`, or the pecl tarball plus phpize/make | same, using the folder's own tools by absolute path. Preflight cc, make, autoconf, pkg-config and the extension's library, printing one platform command if missing (E2). grpc takes the pecl/phpize route |
| Unix slot with `php-config`, not writable (Plesk, Remi, cPanel) | print the command and stop | print the folder-native command (`plesk bin php_handler --extension-install <ext> -id <handler>`, `sudo dnf install php84-php-pecl-<ext>`, or `sudo <folder>/bin/pecl install <ext>`) and stop |
| ondrej binary-path link | print `sudo apt install php8.4-<ext>` | same |
| Enable | slot ini | one ini per extension in PVM's scan dir, absolute `extension_dir`, `zend_extension` decided from the binary; load-check via stderr diff and `php -m`; roll back the ini and restore the old binary on failure |
| Record | source, hash, verified flag | same, plus the backend used and the version constraint, ready for a later `pvm ext upgrade`. Always unverified for PECL, PIE and DLL sources |

The folder model makes no new promises. It removes the one behaviour the user dislikes, the hidden full rebuild, and it lets linked folders use their own extension channel. For Homebrew and pkgx folders that channel needs no sudo, which keeps PVM a thin proxy over the platform's tools.

## What the evidence says about earlier decisions

These are recommendations. Each one needs the user's decision.

| Decision | What the new evidence shows | Recommendation |
|---|---|---|
| **Q2: static-php on Linux/macOS; remove the apt and Homebrew installers** | It **supports** dropping apt installers: they need sudo and are distro-bound, which conflicts with "no sudo". It **challenges** the Homebrew half. Brew needs no sudo, its PHP folders have per-version `pecl`/`phpize`, and the shivammathur tap ships sha256-pinned extension bottles for 5.6–8.7. Those are the only prebuilt and publisher-hashed extensions found. Coverage has narrowed to **Linux x86_64 and macOS arm64; "macOS Intel is not supported"** ([homebrew-extensions README](https://github.com/shivammathur/homebrew-extensions)) | Keep the installer removal, but make `pvm link` first-class and validated, with a convenience such as resolving `brew --prefix php@X.Y`. On a linked brew folder, `ext install` may run `brew install shivammathur/extensions/<ext>@X.Y` as a no-sudo proxy. That is a new behaviour and needs the user's approval |
| **Q5: `bulk` by default** | It **supports** `bulk` for frameworks: it covers 3 of the top 9 PECL extensions plus all the Magento/WordPress bundled ones. The open risk is unchanged: no real `pdo_sqlite`/`pdo_pgsql`, while `common` has them | Keep the condition: switch to `common` if `new PDO('sqlite::memory:')` fails in the smoke test |
| **Q6: fully static musl** | It is **neutral to slightly against**. Under the refusal model, the prebuilt never needs to load a `.so`, so musl's Alpine portability is free. But musl closes the door on alternative 3 (glibc `gnu-bulk` plus PVM-generated headers) for good, and that is the only route to one-extension compiles on a prebuilt | Keep musl if alternative 3 is truly off the table. Pick `gnu-bulk` if a fast xdebug/pcov path on default installs might be wanted later |
| **E1 / draft step 4: rebuild the static slot in place on first extension** | It **challenges** this. The rebuild fires for the commonest asks (xdebug, pcov) and costs minutes plus a toolchain. That contradicts "refuse a single extension over a long full rebuild" | Replace it with refusal plus the two named routes; keep `pvm install X.Y --from-source` as the explicit way to get a full folder |
| **Q1: trust rule** | It holds for PHP: php.net sha256 plus GPG, windows `releases.json`, static-php sidecars. For extensions, **no PECL, PIE or DLL source publishes a checksum** | Keep the rule. Accept that `pvm ext install` will almost always need `--allow-unverified`, word that prompt clearly, and record PIE-style local hashes. Revisit if attestations appear |
| **E3, V1, V2** | They fit the folder model unchanged. Zend API stability within a minor supports keeping extensions across `pvm update` | No change |

## Conclusion

Every platform already has the extensions; what decides whether PVM can install one is whether the slot has `php-config`. Once the slot is defined as a probed folder rather than an install method, the questions about static versus source, Plesk-style folders and which extension backend to use mostly answer themselves. Static-php stays the fast default because it is a folder that cannot build. A source build becomes something the user chooses because they want a folder that can. A Homebrew, Remi or Plesk install becomes an equal citizen with its own native extension route. The remaining costs move to places the user can see: an explicit `--from-source`, a printed sudo command, an `--allow-unverified` prompt.

The decision that most shapes daily experience is not musl versus glibc but what happens on `pvm ext install xdebug` against a default install. The research points to a deliberate refusal with two named routes. The trust rule's collision with an extension ecosystem that publishes no checksums is the next thing the user should settle, before the first extension backend ships. Three things remain unproven and should be tested on real machines first: PIE against a `PHP_INI_SCAN_DIR` set only in the environment, the probe on real Plesk/Remi/pkgx folders, and the `bulk` SQLite smoke test.
